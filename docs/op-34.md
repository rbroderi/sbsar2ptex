# Text Nodes (sbsasm ops 34 and 35)

## Clean-room behavioral specification

This document specifies the compiled Substance **Text** filter: its op
numbers, its node words, the string and font records it points at, and
what it renders. It explains `UnsupportedError: op 34` in Manhole_Cover.
It is intended to be sufficient for an independent implementation
without access to the original implementation. No engine code and no
file data are reproduced; third-party files are cited by name and node
number only.

It was recovered from:

- probe graphs cooked with Designer's `sbscooker` (the `sbsar2ptex.probe`
  helpers, filter `text`): one Text node, with each parameter in turn
  absent, constant or a function reading a float graph input; with and
  without a font (Arial) and a string;
- `sbsrender` renders of those probes at 64, 256 and 1024 pixels,
  compared pixel for pixel with an independent rasterization of the
  font's outlines (section 3);
- a survey of every node of the 35 test archives (5 community files and
  30 cooked-pack files) for ops that have no translator.

Each statement is tagged:

- **[measured]**: established by probes, renders or the survey;
- **[inferred]**: fits the data, but was not tested directly.

`docs/node-seed.md` section 0 defines words, offsets, `rest`, code
blocks and the node word (`flags << 16 | x << 8 | op`); its section 2
places the fields, the seed slot and the size offset.
`docs/node-params.md` section 1 defines parameter states (0 default,
1 inline, 2 function, 3 never seen). This document uses both.

## 1. Identity

**[measured]** Cooking the atomic filter `text` gives op **34** for a
grayscale node and op **35** for a colour node (the filter's
`colorswitch`). They are a gray/colour pair like the other ops: the same
layout, with colour parameters one word wide in op 34 and four in op 35.
No other filter cooks to 34 or 35. (For reference, the other filters
without a translator cook to: `svg` 10 / 11, `bitmap` 32 / 33, the same op
as graph inputs.)

The filter's parameters (Designer 16):

| parameter | type | default | stored |
|---|---|---|---|
| `text` | string | empty | a string record (2.3) |
| `fontdata` | string (a font resource) | empty | a font record (2.4) |
| `fontsize` | float | 0.25 | state word F (2.2) |
| `alignment` | enumeration | 1 | a value in F |
| `matrix22` | float4 | (1, 0, 0, 1) | F |
| `position` | float2 | (0, 0) | F |
| `background` | colour | (0, 0, 0, 1) | F |
| `frontcolor` (font colour) | colour | (1, 1, 1, 1) | F |
| `$tiling` | enumeration | 3 | node word P |

`$pixelsize`, `$pixelratio` and the node's `$randomseed` set alone change
no word **[measured]**.

## 2. Node layout

### 2.1 Node word

**[measured]**

- `op` 34 or 35.
- `flags` bit 0: the node has an output-size function (as every op).
- `flags` bits 6-7: the seed state (`docs/node-seed.md` section 1). A
  constant `randomseed` alone leaves it 0. A parameter function that
  calls `rand` gives state 2 with a seed block (probe: flags 0x0389).
  State 1 was not seen.
- **P** = `flags >> 8` (node-word bits 24-31): bits 0-1 are the
  **tiling** value (0 none, 1 horizontal, 2 vertical, 3 both; default 3),
  a value, not a state. Other bits of P were 0 in every probe and node.

### 2.2 Words after the node word

**[measured]** In file order:

| `rest` index | word |
|---|---|
| 0 | **F**, the parameter-state word (below) |
| 1 | always 0 in every probe and surveyed node (meaning unknown) |
| 2 | the **text** record's offset; 0 when the text is empty |
| 3 | the **font** record's offset; 0 when there is no font |
| 4 | the seed slot, only in seed state 1 or 2 |
| next | the output-size function's offset, only with `flags` bit 0 |
| next | the parameter words, in the order below |
| then | the code blocks |

So the four fields come first, then the seed slot, then the size offset,
exactly as section 2.1 of `docs/node-seed.md` places them for other ops.

**F** holds 2-bit states and one value:

| bits of F | parameter | width of a state-1 value |
|---|---|---|
| 0-1 | never set | |
| 2-3 | background colour | 1 in op 34, 4 in op 35 |
| 4-5 | font colour | 1 in op 34, 4 in op 35 |
| 6-7 | position | 2 |
| 8-9 | font size | 1 |
| 10-11 | matrix | 4 |
| 12-13 | **alignment: a value**, not a state (0, 1 or 2); adds no word | |
| 14-31 | never set | |

Alignment values: 0 left, 1 centre (the default, F = 0x1000), 2 right.
An alignment function was not tried.

**The parameter words** follow the size offset in this fixed order,
which is **not** bit order:

1. background colour;
2. font colour;
3. matrix;
4. position;
5. font size.

For each, by its state: nothing (0), `width` f32 (1), or one offset to a
code block (2). Offsets and f32 values interleave in that order.
Probes: F = 0x2554 (all five constant, alignment 2) reads, in op 34,
background, font colour, the four matrix values, the two position
values, then the font size; in op 35, 4 + 4 + 4 + 2 + 1 words. F = 0x1AA8
(all five functions) reads five offsets whose blocks, in file order,
compute the background, the font colour, the matrix, the position and
the size.

**Colours in op 34** **[measured]**: a constant colour (r, g, b, a) is
stored as one f32, the mean of r, g and b: (0.2, 0.3, 0.4, 0.9) is stored
as 0.3, (0.5, 0.6, 0.7, 1) as 0.6. A colour function is cooked as the
float4 function followed by a dot product with (1/3, 1/3, 1/3, 0) in the
same block, so the block returns a float of width 1. In op 35 a colour
is four f32 (r, g, b, a), and its block returns float4.

Block results **[measured]**: font size float 1; position float 2;
matrix float 4; colours as above.

### 2.3 The text record

**[measured]** At the text offset: a u32 count `n`, then `n` u32 values,
the string's Unicode code points (UTF-32, little-endian). A text of
"AB" is `2, 0x41, 0x42`. A line break is U+000A. Offset 0 points at the
file's word at offset 0, which is 0: an empty string. The records sit in
the data area before the nodes; reach them only through the offset.

### 2.4 The font record

**[measured]** At the font offset: a u32 (an identifier of the font; its
meaning is unknown), a u32 byte length `L`, then `L` bytes: the whole
font file (a TrueType file for Arial, starting with the sfnt version
0x00010000). The cooker embeds the font that `fontdata` names. Offset 0
means no font was embedded.

### 2.5 Survey

**[measured]** Of all ops in the 35 archives, the only ones with no
translator (graph inputs 32 / 33 aside) are op 34 nodes: 4 nodes, all in
Manhole_Cover (n694, n713, n732, n751). Op 35 does not occur. No other
untranslated op occurs in any of the 35 archives.

All four Manhole nodes have the same shape: node word 0x03198822 (tiling
3, size function, seed state 0), F = 0x1100 (font size constant,
alignment 1, everything else default), `rest[1]` 0, a non-empty text
record (23, 16, 21 and 11 code points), **font offset 0**, the size
offset, then one f32, the font size 0.015. With no font, each renders as
its default background (section 3.1): a uniform 0.

## 3. Semantics

### 3.1 No ink: a uniform fill

**[measured]** When nothing would be drawn, the node is filled with its
background colour, exactly as a Uniform Color node of that colour is
filled (including its 8-bit rounding: background 0.3 gives 77, and
1.3 / 3 gives 111, the uniform fill's values, not a drawn store's).
"Nothing drawn" covers every case probed:

- no font (font offset 0), with or without text;
- a font and an empty text;
- a font and a text whose glyphs have no outline (a single space).

In op 34 the value is the stored gray (the mean of r, g, b); in op 35 the
four channels. With the default background the result is 0 (gray) or
(0, 0, 0, 1).

### 3.2 With ink: layout

**[measured]** unless marked. Let:

- `N` be the output width in pixels (square outputs were probed);
- `upm`, `asc`, `desc`, `gap` the font's units per em, ascender,
  descender (negative) and line gap (Arial: 2048, 1854, −434, 67; its
  horizontal-header and Windows metrics agree, so which table is read is
  unknown);
- `s = fontsize / (asc − desc)` the scale from font units to image units
  (UV, the image being 1 × 1). The font size is the line's
  ascender-to-descender height, not the em: at 0.25, Arial's cap height
  (1466 units) is 0.1602 of the image.
- `A = (0.5, 0.5) + position` the **anchor**, in UV with y down.

Lay out each line (split at U+000A) in font units, x to the right, y up:

1. Each glyph's pen position is the sum of the previous glyphs' advance
   widths plus the font's kerning between each pair (Arial's A–V pair
   moves V left by 152 units; rendering without kerning is off).
2. The line's ink extent: `x0` = the smallest, `x1` the largest x of any
   glyph outline point, pen positions included. `W = x1 − x0`.
3. The line's pen origin is `−a · W` in units of `s`, with `a` = 0, 0.5 or
   1 for alignment 0, 1 or 2. That is, the ink box's width is aligned,
   but the box is placed from the first glyph's pen, not from its ink:
   the ink begins `xMin(first glyph)` to the right of the aligned edge.
   (Arial "H", centred, has its ink centred 164 units · s right of the
   anchor: 0.0179 at size 0.25.)
4. Line `k` (from 0) has its baseline `k · (asc − desc + gap)` font units
   below the first line's.

Then a glyph point `(gx, gy)` of line `k`, in font units relative to that
line's pen origin, sits at the local offset

```text
d = ( gx · s ,  (k · (asc − desc + gap) − gy) · s )     (UV, y down)
```

and the **matrix** maps output to that local frame. For an output point
`uv`, with `(dx, dy) = uv − A`:

```text
local = ( m0 · dx + m2 · dy ,  m1 · dx + m3 · dy )
```

where `matrix22 = (m0, m1, m2, m3)` in stored order. The output pixel at
`uv` shows the glyph ink at `local`. Measured: (2, 0, 0, 1) halves the
text's width about the anchor; (0, 1, −1, 0) turns it a quarter turn (the
baseline becomes the vertical line through the anchor, the letters to
its left); (1, 0, 0.5, 1) slants it. The position is applied after the
matrix: with (2, 0, 0, 1) and position (0.1, 0) the half-width text moves
by 0.1, not 0.05. **[inferred]** The line offset `k` sits inside the
matrix as written (multi-line text was measured only with the identity
matrix).

**Tiling** (P bits 0-1): with tiling 3 the ink wraps around both edges
(coordinates taken modulo 1); 1 wraps horizontally only; 2 vertically
only; 0 clips at the edges. **[measured]** for 0, 1 and 3 horizontally,
and 2 clipping horizontally; vertical wrapping was not isolated.

### 3.3 With ink: pixel values

**[measured]**

- **Coverage.** Each output pixel `[i, i + 1) × [j, j + 1)` (pixel units,
  `j` down) gets `c`, the exact area of that square covered by the
  laid-out outlines (filled by the nonzero winding rule, outer contours
  minus holes), clamped to [0, 1]. Then `c8 = round(255 c)` (nearest).
  No hinting and no snapping: an Arial "H" (straight edges only) matches
  this to the last 8-bit level at every pixel at 256 and 1024 pixels,
  and at several positions and matrices. A "k" (diagonal edges) matches
  except for 1 pixel off by one level at 1024 pixels.
- **Curves.** Quadratic outline segments are flattened into straight
  chords before the coverage is taken. The rule is not established:
  flattening each curve until the chord is within 0.35 to 0.40 pixel of
  the curve's midpoint (repeated halving) comes closest (Arial "O" at
  1024: 663 pixels off, by at most 24 levels), while very fine
  flattening leaves 1,200 pixels off by up to 109 levels. See section 5.
- **Colour.** Per channel:

  ```text
  value = background + (fontcolor − background) · c8 / 255
  ```

  (op 34: the stored grays; op 35: r, g, b and a separately, alpha
  included). The font colour's alpha is a channel like any other; it
  does not weight the mix.
- **Storing.** The value is stored as a drawn node's 8-bit output is,
  not as a uniform fill: background pixels away from the text, with
  background 0.3, read 76 (a fill gives 77). On the probe machine the
  stores matched the AMD rule of `fxglsl.level8_glsl` (through a half
  float's 11 bits, truncated, then the nearest) at every pixel, in
  gray and colour. **[inferred]** On other GPUs, as other drawn nodes
  store there.
- **Resolution.** The layout is in UV and does not depend on `N`; the
  coverage is taken at the output's own resolution.

### 3.4 What a translator needs for the corpus

All four corpus nodes (Manhole_Cover) have no font, so each is exactly a
uniform fill of its background colour (3.1): here the default, 0. The
font size, alignment and text are irrelevant then. Rendering text with
ink needs the embedded font file (2.4), its outlines, advances and
kerning; nothing in the corpus does.

## 4. Acceptance tests

Synthetic nodes; each node starts at offset 0x100. Words are given from
the node word on (`w0`; `w1` is `rest[0]`). "→ X" is an offset word
pointing at a well-formed block or record X later in the node or file:

- `SZ`: a size block (integer width 2);
- `F1`, `F2`, `F4`: float blocks of width 1, 2 and 4;
- `SB`: a seed block (integer width 1);
- `T`: a text record; `FT`: a font record.

Floats are f32 bit patterns: 0.015 is 0x3C75C28F, 0.3 is 0x3E99999A
(0x3E999999 as the cooker's mean), 0.6 is 0x3F19999A (0x3F199999),
2.0 is 0x40000000, 0.5 0x3F000000, 0.25 0x3E800000, 3.0 0x40400000,
0.1 0x3DCCCCCD, 0.2 0x3E4CCCCD.

**Layout**

1. **Defaults.** Op 34, `w0 = 0x03098822`; `0x00001000`, 0, 0, 0,
   → `SZ`. Gray; tiling 3; alignment 1; every parameter default; empty
   text; no font. No inline values.
2. **The Manhole shape.** `w0 = 0x03198822`; `0x00001100`, 0, → `T`, 0,
   → `SZ`, 0x3C75C28F. Font size 0.015 (F bits 8-9 = 1); alignment 1;
   text from `T`; no font.
3. **All constants, gray.** `w0 = 0x03098822`; `0x00002554`, 0, → `T`,
   0, → `SZ`, 0x3E999999, 0x3F199999, 2.0, 0.5, 0.25, 3.0, 0.1, 0.2,
   0x3E99999A. Background 0.3; font colour 0.6; matrix (2, 0.5, 0.25,
   3); position (0.1, 0.2); font size 0.3; alignment 2 (right). Reading
   the parameters in bit order (position before the matrix) is wrong.
4. **All constants, colour.** Op 35, `w0 = 0x03098823`, same F: after
   → `SZ`, background 4 f32, font colour 4 f32, matrix 4 f32, position
   2 f32, size 1 f32: 15 words.
5. **All functions.** `w0 = 0x03098822`; `0x00001AA8`, 0, 0, 0, → `SZ`,
   → `F1` (background), → `F1` (font colour), → `F4` (matrix), → `F2`
   (position), → `F1` (size). In op 35 the two colour blocks are `F4`.
6. **A seed block.** `w0 = 0x03898822`; `0x00001200`, 0, 0, 0, → `SB`,
   → `SZ`, → `F1`. The seed slot is `rest[4]`; size `rest[5]`; the font
   size function `rest[6]`.
7. **Tiling 0.** `w0 = 0x00098822`, otherwise test 1: tiling 0, no
   extra word.
8. **No size function** **[inferred]** (every probe and corpus node has
   one). `w0 = 0x03088822`; `0x00001100`, 0, 0, 0, 0x3C75C28F: the size
   f32 directly after the fields.
9. **Text record.** At `T`: `2, 0x41, 0x42`: the text "AB". At `T`:
   `3, 0x48, 0x0A, 0x48`: two lines, "H" and "H".
10. **Font record.** At `FT`: `id, L`, then `L` bytes, the font file.
11. **Rejections.** A state 3 in any 2-bit field of F, an alignment of
    3, a set bit 0-1 or 14-31 of F, or a non-zero `rest[1]` is
    unknown: report it.

**Semantics**

12. **No font, colour.** Op 35, background (0.2, 0.3, 0.4, 0.9) (F bits
    2-3 = 1), text "AB", font offset 0: every pixel of an 8-bit output is
    (51, 77, 102, 229). The same with a font and an empty text, or with
    a font and the text " ".
13. **No font, background function.** Op 35, background function
    returning (v, v, v, v): v = 0.3 gives 77 in every channel; v =
    0.43333334 gives 111; 0.1 gives 26; 0.7 gives 178. The same in op 34
    (the function's mean).
14. **Manhole.** Test 2's node with any text: a uniform 0.
15. **Layout of "H".** A font with `upm` 2048, `asc` 1854, `desc` −434,
    `gap` 67, whose "H" is the 12-point contour (164, 0), (164, 1466),
    (358, 1466), (358, 864), (1120, 864), (1120, 1466), (1314, 1466),
    (1314, 0), (1120, 0), (1120, 691), (358, 691), (358, 0), advance
    1479. Font size 0.25, alignment 1, defaults otherwise, N = 1024:
    - `s = 0.25 / 2288`. The ink extent is W = 1314 − 164 = 1150, so
      the pen origin is −575 s, and the ink spans
      [0.5 − 575 s + 164 s, 0.5 + 575 s + 164 s] = [0.45509, 0.58075] in
      x and [0.5 − 1466 s, 0.5] = [0.33982, 0.5] in y;
    - pixel (x 466, y 400) has coverage 0.98588: 8-bit 251; the
      neighbours (465, 400) and (467, 400) are 0 and 255.
    - With text "H\nH", the second H's baseline is at 0.5 + 2355 s
      = 0.75733.
    - With alignment 0 the ink starts at 0.5 + 164 s = 0.51792; with
      alignment 2 it ends there.
    - With matrix (2, 0, 0, 1) the ink spans [0.5 + (−575 + 164) s / 2,
      0.5 + (575 + 164) s / 2] in x.
16. **Colour mix.** Test 15 with background 0.3 and font colour 0.6
    (op 34): pixel (466, 400) is 152; inside the stem, 153; away from
    the text, 76 (a drawn store, not the fill's 77). In op 35 with
    background (0.2, 0.3, 0.4, 0.9) and font colour (0.5, 0.6, 0.7,
    0.8): (126, 152, 177, 204) at (466, 400), (128, 153, 178, 204) inside,
    (51, 76, 102, 229) outside.

## 5. Unknown

- **`rest[1]`** is 0 in every probe and node.
- **F bits 0-1** never change in any probe.
- **The font record's first word** (an identifier; its derivation was
  not studied).
- **Curve flattening.** Straight edges are exact (3.3); the rule that
  turns quadratic segments into chords is not established. An
  implementation that cannot match it should expect edge pixels of
  curved glyphs to be off by tens of levels.
- **Font metrics source.** Arial's horizontal-header and Windows metrics
  are equal; which one sets `asc`, `desc` and `gap` is untested. So is a
  font with CFF outlines, or one without a kerning table but with
  positioning tables (Arial has both; which was used is untested).
- **Non-square outputs**, vertical tiling alone, alignment of lines of
  different ink widths with the matrix, glyphs missing from the font,
  and code points above U+FFFF were not probed.
- **Alignment as a function** and **tiling as a function** (folded to
  constants for other ops) were not tried.
- **GPU differences.** Stores were measured on one machine (AMD rule).
- **Output formats** other than the default 8-bit were not probed.
